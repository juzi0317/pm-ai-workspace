# AI 产品 UI 全流程

使用这个 skill，把一个产品想法按顺序推进成可交付的 UI 资产：

**产品想法 -> PRD -> 黑白原型 -> 主视觉稿 -> 视觉规范/可选 IP 规范 -> 全页面 UI。**

核心原则：**不要从一句模糊想法直接生成最终 UI。** 先把产品需求结构化，再用黑白原型锁定页面结构，最后用风格参考图迁移视觉风格。

## 默认工作方式

默认使用中文输出，除非用户指定其他语言。

如果用户要完整流程，按阶段依次推进。如果用户只要其中一个阶段，也要让产物兼容后续完整流程。

完成黑白原型后设置一个自然停靠点：请用户确认是否继续进入高保真视觉阶段。如果用户不继续，整理并交付 PRD 与黑白原型，直接结束本次流程。只有当用户明确要求"一口气跑完整流程"时，才在说明假设后继续推进。

如果用户提供 Figma 链接、截图、图片文件夹、PRD、HTML 或 Markdown 规范，先阅读这些材料，再开始生成。保留用户原始素材，在新项目目录中输出新文件。

只有当缺失信息会明显影响方向时，最多问 3 个澄清问题。否则先做合理假设并继续执行。

## 输入信息

收集或推断以下信息：

- 产品名称与一句话概念
- 目标用户、使用场景、平台类型：移动端 App、网页、后台、小游戏、小程序等
- 核心用户目标与 3-5 个 MVP 功能
- 必要页面或核心用户流程
- 期望风格方向或参考图片
- 输出目标：PRD、HTML 原型、UI 图、视觉规范、可选 IP 规范、完整 HTML UI、Figma-ready 文件等

如果用户只有一个很粗的想法，先输出一个简短产品概念摘要，让用户确认后再进入完整 PRD。

## 推荐目录结构

为每个项目创建分阶段目录：

```text
project-name/
  00-source/
  01-prd/
    product-prd.md
  02-wireframe/
    index.html
    styles.css
    screenshots/
  03-visual-direction/
    references/
    main-screens/
    direction-notes.md
  04-specs/
    visual-spec.md
    ip-character-spec.md        # optional
    asset-pack-manifest.md      # optional
  05-final-ui/
    index.html
    styles.css
    assets/
    screenshots/
  06-handoff/
    figma-notes.md
    export-checklist.md
```

把用户给的原图、参考图、PRD、Figma 导出素材放进 `00-source/`。不要覆盖原始文件。

## 阶段 1：产品想法到 PRD

目标：把模糊想法变成可执行的产品需求文档。

输出 `01-prd/product-prd.md`，内容包括：

- 产品定位与目标用户
- 用户场景与用户任务
- MVP 范围与暂不做的内容
- 信息架构与页面清单
- 核心用户流程
- 每个页面的功能需求
- 字段、状态、空状态、错误状态、边界情况
- 内容语气与示例文案
- 验收标准

质量检查：

- 每个页面都必须有页面目标、主操作、核心内容和状态覆盖。
- PRD 必须具体到可以直接生成黑白原型，不需要后续大量脑补。
- 如果 PRD 提到视觉，只保留关键词，不要在这个阶段解决 UI 风格。

## 阶段 2：PRD 到黑白 HTML 原型

目标：先锁定产品结构，再做视觉。

基于 PRD 创建黑白低保真原型。移动端 C 端产品默认遵循 User 12 / 十二 C 端移动端低保真规范；非移动端产品按目标平台建立对应低保真结构。需要可修改、可录屏、可导入设计软件或后续转 Figma 时，优先输出 HTML/CSS。

规则：

- 只使用黑、白、灰、间距、层级和真实文案。
- 不使用品牌色、渐变、插画、强装饰阴影或完整视觉系统。
- 覆盖 PRD 中的主要页面、核心流程和关键状态。
- 页面区块和组件命名要清楚，方便后续修改。
- 保证目标视口下布局稳定。

质量检查：

- 不靠装饰也能看懂产品流程。
- 原型要回答：有哪些页面、每页做什么、用户怎么流转。
- 如果结构不清楚，不要进入高保真阶段。

阶段停靠点：

- 完成黑白原型后，给用户一个简短选择：继续进入主视觉稿，还是先停在 PRD + 黑白原型。
- 如果用户选择暂停或不继续，输出文件路径、使用方式、已完成检查和后续可继续的入口，不再自动生成视觉稿。
- 如果用户选择继续，进入阶段 3，并要求用户提供或确认风格参考图。

## 阶段 3：黑白原型 + 风格参考图到主视觉稿

目标：用已经锁定的黑白原型，加上风格参考图，生成主要页面的高保真 UI。

输入：

- 黑白原型截图或 HTML
- 一个或多个风格参考图
- 产品关键词、目标用户和情绪氛围

方法：

1. 把黑白原型当成结构来源。
2. 把风格参考图当成视觉来源。
3. 保留原型里的页面布局、信息层级和核心交互。
4. 迁移参考图里的颜色、字体气质、形状语言、质感、插画/IP、图标、光影和氛围。
5. 如果用户还没选风格，先生成 2-4 个风格方向。

质量检查：

- 高保真稿仍然能对应回原型结构。
- 风格特征必须明显，不能只是泛泛的"干净简约"。
- 视觉必须适合产品用户和使用场景。
- 不接受"很好看但功能丢失"的图。

## 阶段 4：提取视觉规范与可选 IP 系统

目标：把选定的主视觉稿，变成可复用的设计规则。视觉规范是默认产物，IP 形象规范只在产品确实包含角色、吉祥物、头像、贴纸、插画系统或用户明确要求时生成。

输出 `04-specs/visual-spec.md`，包含：

- 设计关键词和整体气质
- 色彩 token：hex、使用场景、禁用方式
- 字体、字号、字重、行高规则
- 间距、圆角、描边、阴影、卡片和层级规则
- 组件规范：按钮、卡片、输入框、导航、标签、列表、弹窗等
- 图标、插画、图片和动效风格
- 页面构图规则
- Do / Don't 示例

当产品包含 IP、角色、头像、吉祥物、贴纸或插画系统时，输出 `04-specs/ip-character-spec.md`，包含：

- 角色定位和性格
- 身体比例、轮廓、颜色、五官、材质和线条
- 表情系统
- 姿势和动作系统
- 场景使用规则
- 贴纸包或拓展素材包规划
- SVG 或图片资产命名规则
- Do / Don't 示例

如果生成了素材包，输出 `04-specs/asset-pack-manifest.md`，记录：

- 文件名
- 素材类型
- 使用场景
- 格式
- 尺寸或视口
- 来源提示词或来源图片引用

质量检查：

- 另一个设计师或 AI agent 应该能根据规范继续生成一致的页面。
- 规范必须从已选视觉稿中提取，不要写成通用设计理论。

## 阶段 5：规范 + 原型到最终全页面 UI

目标：结合 PRD、黑白原型、选定主视觉、视觉规范和可选 IP 资产，生成完整高保真页面。

输出 `05-final-ui/`，包含：

- PRD 中定义的完整页面清单
- 共享组件和视觉 token
- 真实文案与关键状态
- 与主视觉稿一致的风格
- 可交付资产目录
- 用于检查的截图

规则：

- 如果用户需要可编辑文件，不要把最终 UI 做成单张大图。
- 用黑白原型决定页面结构，用视觉规范决定风格。
- 只有在存在 IP 规范或 IP 资产时，才把 IP 系统作为最终 UI 的约束。
- 跨页面复用组件。
- 页面命名要和 PRD、原型保持一致。

Figma-ready 交付：

- 如果有 Figma 工具，并且用户要求 Figma 文件，基于最终 UI 创建或更新 Figma 节点。
- 如果没有 Figma 工具，输出结构清晰的 HTML/CSS/资产目录，并补充 `06-handoff/figma-notes.md`。
- 除非用户只要预览图，否则不要用整页背景图伪装成可编辑 UI。

质量检查：

- 对照 PRD 页面清单，确认没有漏页。
- 检查视觉 token 是否一致。
- 检查图片路径、响应式视口、文字溢出、缺失状态。
- 能截图就截图，并做视觉检查。



## 教学与公开提示词

提示词模板可以作为公开内容使用。当用户需要可复制提示词、教学资料、提示词包或面向客户的版本时，读取：

`references/prompt-templates.md`

在教程或宣传场景中，优先展示真实产物：PRD、黑白原型、主视觉稿、视觉规范、全页面 UI。不要把这套方法包装成单条万能提示词；它的价值是分阶段交付和可复用流程。

## 最终回复格式

每完成一个阶段，简洁说明：

- 产出了什么
- 文件在哪里
- 做了哪些假设
- 下一阶段前需要用户确认什么
- 做过哪些质量检查

不要在聊天里粘贴超长文档，优先指向文件路径。
